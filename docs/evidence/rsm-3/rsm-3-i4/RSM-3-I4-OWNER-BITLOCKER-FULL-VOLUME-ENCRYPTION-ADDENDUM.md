## 1. Reason for the Correction

PRE2 established that the selected Seagate is:

```text

healthy
accessible
NTFS
FullyDecrypted
0% encrypted

```

The selected volume is an existing external device and current authority does not prove that it has never previously contained confidential unencrypted data.

For an existing or repurposed volume, free space can contain recoverable remnants of previously deleted plaintext data.

Therefore the prior new-encryption choice:

`Used Space Only`

is superseded for this exact selected volume.

## 3. BL-01 — Encryption Configuration

Required configuration for the exact selected volume:

```text
Encryption mechanism = Microsoft BitLocker software encryption
Encryption method = XTS-AES 256
Encryption extent = FULL VOLUME ENCRYPTION
UsedSpaceOnly = FALSE
Hardware encryption = NOT REQUESTED
Automatic unlock = DO NOT ENABLE
```

No formatting, repartitioning, deletion, or filesystem conversion is authorized.

---

## 4. BL-02 — Protector Configuration

Required final protector set:

```text
Primary protector = Password
Recovery protector = Recovery Password
```

The primary password:

- is chosen interactively by the owner;
- must not be written to repository/bootstrap/evidence;
- must not be printed by the script;
- must not be supplied to ChatGPT/Codex;
- should be a strong non-reused passphrase.

The Recovery Password:

- is generated by Windows;
- must not be printed into evidence;
- must not be pasted into ChatGPT/Codex;
- may exist transiently only in local process memory / clipboard for owner custody transfer;
- must be stored in a secure location logically/physically separate from both the workstation and the selected Seagate volume;
- clipboard must be cleared after owner attestation.

---

## 5. BL-03 — Owner Custody Attestation

After the Recovery Password has been saved separately, the owner must locally attest exactly:

`RECOVERY_MATERIAL_STORED_SEPARATELY = TRUE`

The attestation evidence may contain:

- selected Volume GUID;
- safe Recovery Password protector ID;
- owner Windows identity;
- UTC/local timestamp;
- the attestation sentence;
- confirmation that no secret is included.

It must not contain the Recovery Password itself.

---

## 6. BL-04 — Mutation Boundary

The authorized owner-only mutation is limited to:

1. exact selected-volume identity verification;
2. BitLocker enablement with `XTS-AES 256` and full-volume encryption;
3. creation of one Recovery Password protector;
4. creation of one Password protector;
5. owner custody transfer/attestation;
6. safe read-only status observation after start.

It does NOT authorize:

- repository mutation;
- Git push;
- backup creation;
- clean clone;
- restore;
- source 07 creation;
- auto-unlock;
- protector deletion;
- filesystem mutation;
- volume formatting.

---

## 7. BL-05 — Post-Mutation Acceptance

BL1 does not itself declare the external backup gate closed.

A later Administrator read-only verification must prove:

```text
selected volume identity = exact
VolumeStatus = FullyEncrypted
EncryptionPercentage = 100
EncryptionMethod = XtsAes256
ProtectionStatus = On
LockStatus = Unlocked or otherwise valid for intended controlled backup
Password protector = PRESENT
RecoveryPassword protector = PRESENT
AutoUnlockEnabled = FALSE
owner custody attestation = PRESENT / exact
```

If full-volume encryption is still in progress, the later verification must remain blocked without changing the volume.

Only after these gates pass may the actual RSM-3-I4 execution begin.
